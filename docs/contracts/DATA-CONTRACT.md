# Legendary Memory data contract — draft v0.1 (2026-11-19)

Status: **approved by Daniel 2026-11-19** (execution plan P1.1–P1.2); §10 decisions recorded below. Each rule is marked:

- **Current** — what the code on `main` (`8d7d048`, schema v1) does today.
- **Target** — what P2/P3 will implement. Changing stored records waits for owner approval of this file.
- **Decide** — a product choice for Daniel; a recommendation is given.

Every rule names the test that proves it. "Hub" means any home: local file, self-hosted, Cloudflare.

## 1. Record types and identity

| Record | Identity (portable across homes) | Current behavior | Target |
|---|---|---|---|
| Project | `id` (UUID, kept by `copy`), unique `slug` from name | Name lookup is exact → alias → fuzzy | Same, plus confirmation for ambiguous writes (§4) |
| Brief | One per project, `projects.brief` | Rewritten in place; previous text saved to `brief_versions`, newest **10** kept | Keep 10; add `revision` integer for conflict checks (§3) |
| Brief version | `(project_id, replaced_at, brief)` | Autoincrement `id` is local only | Same; never used as a cross-home id |
| Checkpoint | `id` (UUID) | Immutable after save | Same. Corrections are new checkpoints that supersede (§5) |
| Artifact | `id` (UUID); unique `(project_id, name)` | Saving the same name overwrites `content`, bumps `version`; **old bodies are not kept** | **Decide** whether to keep N old bodies. Recommend: keep the latest only (today's behavior) until a user asks; storage stays bounded |
| Profile fact | `key` | Upsert by key | Same |
| Conversation | `(source, external_id)`; local `id` UUID | Upsert; `source` ∈ chatgpt, claude, gemini, other | Add `codex` and `cursor` to `source` (found by the P1 fixtures: Codex history must be filed as `other` today) |
| Message | `(conversation, seq)` | Upsert: re-sending rewrites text **and re-indexes every message** in the batch | Hash `(role, text)`; skip unchanged rows and their index rows (§3, P2.2) |

Rules:
1. Ids are generated once, by the home that first stores the record, and never change. `copy`, `backup` and restore keep them.
2. Autoincrement ids (`brief_versions.id`, `messages.id`, `search_map.id`) are local and must never appear in a ref, export key or manifest. Proven by `hub/scripts/manifest.py` and `backup.ts`, which hash without them.
3. The search index (`search_map`, `search_fts`) is derived. It is never exported, never compared, and can be rebuilt from canonical tables at any time.

## 2. Provenance

Current: checkpoints and artifacts store `source` (the client that wrote them, e.g. `claude`, `chatgpt`, `codex`); conversations store their provider and original URL and start date.

Target:
- Every write records `source` and `created_at` (already true) and, for imported chats, the importer adapter version.
- Imported original text and generated summaries stay distinguishable: chats live in `conversations/messages`; checkpoints are always generated by an assistant. No feature may turn one into the other silently.

## 3. Writes that are safe to retry

| Operation | Current | Target |
|---|---|---|
| `save_checkpoint` | A retry after a lost response saves a **second identical checkpoint** | Optional `idempotency_key` (client-generated); same key within 24 h returns the first result |
| `save_artifact` | A retry bumps `version` again with the same content | No-op when content is byte-identical (no version bump, no reindex) |
| Brief update | Last write wins | Optional `expected_revision`; mismatch returns "brief changed since you read it" with the current text |
| Chat import | Idempotent in rows, **not in work**: every resend rewrites and re-indexes all sent messages | Skip unchanged messages by hash; resending identical history performs zero index writes |
| `copy` | Idempotent; never deletes | Same (it is an additive tool, not a sync) |

Measured baseline (bench/out/*.report.json, synthetic data, 2-vCPU Linux):
- 10K messages: each identical re-import rewrites ~10.8K index rows; after 10 re-imports the file is 32 MiB larger with the same records.
- 100K messages: each identical re-import rewrites ~106K index rows and takes ~33 s; after 3, the file is 154 MiB larger.

Acceptance (P2.2): ten identical imports leave record counts, canonical bytes and index row ids unchanged; one edited message changes exactly one message row and its index rows.

## 4. Project names (reads vs writes)

Current: reads and writes both resolve a loose name to the single closest project. Reads label fuzzy matches ("closest match for …"). **Writes never ask.** Baseline: writing to `cookin` with both *Cooking Club* and *Cooling Rig* present filed silently into *Cooking Club*.

Target:
1. Exact name, slug or alias → that project (reads and writes).
2. One fuzzy candidate clearly ahead → reads use it and label it; writes use it and say which project they used.
3. Two or more plausible candidates → reads show the best and list the others; **writes refuse** and return the candidates, asking the assistant to repeat with the exact name. No record is written.
4. No candidate → reads say nothing matched; `save_checkpoint` creates a new project only when the name matches nothing (today's behavior).

Judged cases live in `bench/fixtures.mjs` (`project-name` kind).

## 5. Corrections, archive and deletion — four different things

| Action | Meaning | Current | Target |
|---|---|---|---|
| Correct | A fact or decision changed | Write a new checkpoint or edit the brief | Same; recall prefers the newest; the old one stays visible as history |
| Archive | Keep, but stop surfacing by default | `projects.status = archived` | Same; archived projects stay searchable when asked |
| Delete (`forget`) | Remove one item now | Hard delete of the row and its index rows. Project delete cascades to its briefs, checkpoints and artifacts; its chats stay, unfiled | Same, **plus** a deletion record (§6) |
| Erase account | Remove everything a hosted account holds | Not built | P7/P9: live data now; provider backups by their published window |

## 6. Deletions must survive restores and copies

**Implemented 2026-11-19 (schema 3, `migrations/0003_deletions.sql`, tested by `hub/test/deletions.mjs`).**
Before that, deletes left no trace and an older backup or another home could bring them back.

Target (P3/P9):
- New table `deletions(kind, ref, deleted_at)` — identity only, no content. Not restorable content: it is kept outside the memory export's restorable rows and re-applied after any restore.
- `copy` and restore skip rows whose identity is in the destination's `deletions`, and report how many they skipped.
- `copy` carries the ledger: deletions on the source are applied on the destination and reported ("N removed here").
- A deliberate `remember` of a deleted key clears that key's entry (a new fact). New saves get new ids, so they are never blocked.
- Known limit: restoring an old backup into an **empty** home cannot know about later deletions; copy from the current home afterwards (or restore into it) and they are removed. P3.5's quarantined restore will make this automatic.

Acceptance: delete a checkpoint, restore a backup taken before the delete, the checkpoint stays deleted.

## 7. Versions

Three version numbers, changed independently:

| Version | Today | Rule |
|---|---|---|
| Schema (`PRAGMA user_version`) | 1 | Migrations only forward. Older binaries refuse newer files without changing them (already tested in `test/db.mjs`). |
| Portable archive | none (copy/backup produce a SQLite file + `manifest.json` format 1) | P3.3: compressed archive with `archive_version`, schema version, manifest, attachment list, checksums. Restore must accept every archive version still advertised. |
| Tool/API contract | Implicit (7 tools) | Add `contract_version` to the MCP server `instructions`. Removing or renaming a tool argument is a breaking change: announce, support both for one minor release. |

## 8. Permissions (input to P4)

| Scope | Tools |
|---|---|
| read | `recall`, `search`, `read` |
| write | `save_checkpoint`, `save_artifact`, `remember` |
| delete | `forget` (and account erase on hosted) |

**Implemented 2026-11-24 (PR #10):** the approval page offers read, save and delete separately (delete unchecked by default); the server enforces them on every tool call. Connections approved before this keep "write implies delete" (they carry no `v: 2`), so existing apps do not break. Local stdio and `serve` keep all three.

## 9. Limits that are part of the contract

| Limit | Current | Target |
|---|---|---|
| Searchable text per item | First **8,000 chars** only (baseline: 0/20 phrases past char 8,000 found, 10K and 100K fixtures) | Whole text, in bounded chunks that reference the original (P2.4) |
| Ingest request | ≤ 2,000 messages, ≤ 1.5 MB | Same; clients split long chats |
| Read page | 500–40,000 chars, default 8,000 | Same; long items always paginate, never truncate the stored source |
| Recall reply | Clamped to a token budget | Default target ~2,000 tokens (P1.3 measurement: ~900 chars at baseline) |

## 10. Decisions (Daniel, 2026-11-19)

1. Artifact history: **keep the latest only** (today's behavior).
2. Ambiguous project names on writes: **refuse and list the candidates**; nothing is saved.
3. Deletion ledger: **kept forever** (identity only, no content).
4. Chat sources: **add `codex` and `cursor`**.

These unlock the P2 changes (incremental import, chunked search, name confirmation) and the P3 deletion ledger.
