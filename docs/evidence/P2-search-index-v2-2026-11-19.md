# P2.3 / P2.4 — search index v2: no duplicate text, whole-text search — 2026-11-19

Change: `migrations/0002_search_v2.sql` plus matching code (branch `p2-search-index-v2`).

- The full-text table is **contentless**: it indexes words but no longer stores a second copy of
  every body. Titles and snippets are read from the records when a search returns them.
- Long text is indexed in **4,000-character chunks overlapping by 200**, so every word is
  searchable (was: first 8,000 characters only). Hits are grouped so one long item is listed once.
- The migration rebuilds the index from the canonical tables in SQL (works on D1 via
  `wrangler d1 migrations apply`, and locally on first open). Records are never changed.

## Tests

`hub/test/search-v2.mjs` (27 checks, in `test:all`) upgrades a committed 1.0.2 fixture
(`test/fixtures/v1-memory.db`, synthetic, regenerated by `make-v1-memory.mjs`):
records hash identically before/after; the migrated index equals the index a fresh install builds
(same rows, same matches for six queries); text past 8,000 chars is found in a file and in a chat
message; a long item is listed once with a matching snippet; an edit removes the old words of every
chunk; no text copy is stored; the work table is gone; compact runs; Russian and stemming still work.

## Bug found and fixed on the way

`copy --from <file.db>` opened the source with the normal open path, which **upgraded the source
file in place** (and switched it to WAL). Harmless with one migration; with two it would silently
rewrite a backup being restored. `copy` now reads a private snapshot of any source file; the test
checks the 1.0.2 fixture is byte-identical after being restored from.

## Before deploying to the Cloudflare hub (owner approval needed)

1. Fresh `legendary-memory backup` of the hub (and note D1 Time Travel, 30 days, as a second net).
2. `wrangler d1 migrations apply DB --remote` then `wrangler deploy` with the same build.
   Contentless FTS5 with `contentless_delete` was verified on wrangler's local D1 engine; it has not
   been run on production D1 yet. If production rejects it, the migration fails before any change
   is committed and the Worker stays on schema 1.
3. Run recall/search from Claude and ChatGPT; take another backup and compare memory hashes.
4. The Mac backup tool must be on this build too: a 1.0.2 CLI refuses schema-2 files (by design).
